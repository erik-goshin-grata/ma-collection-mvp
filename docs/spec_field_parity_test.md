# Spec: Field parity test

**Status: checks 2–4 UNGATED (2026-08-11); check 1 superseded.** Per
`docs/workorder_code_2026_08_11.md`, checks 2–4 test this repo's internal consistency and never
depended on Grata, so their ON HOLD gate is lifted; building `scripts/test_field_parity.py` is
the natural follow-on to phase 1. The allow-list below is declared now (work order step 2). The
former blanket ON HOLD — pending eng-team schema/enum locations — applied to the field-inventory
generation, which remains the sequencing precondition for a full run.

**Purpose:** catch field-level drift the way `test_reason_code_parity.py` catches enum drift.
**Deliverable:** `scripts/test_field_parity.py`
**Pattern:** mirrors the existing parity tests. Not a reference document — a test that fails.

**Sequencing:** definition precedes parity. The field inventory — generated by origin, per
`decisions.md` "Field Inventory Method and Naming Conventions" — comes first. A parity test over
an undefined field set checks consistency without checking correctness.

---

## Why

A field's definition is spread across up to six places: the extraction prompt, the parser, the
`staging_extraction` column, the aggregation read (`_FIELDS`), the observation read
(`HC_FIELDS`), and two schema files (`001_initial.sql` CREATE TABLE and the `db.py`
`_apply_migrations` list).

Nothing checks that they agree. Two divergences surfaced on 2026-08-10 alone:

- **`round_size` missing from `HC_FIELDS`** — present on the staging read path, absent on the
  observation path. Would have nulled `investment_amount` for every minority raise on the
  observation loader. Caught by hand; fixed in `e66c88c`.
- **`investment_amount` and `deal_value_currency` missing from `001_initial.sql`** — present in
  the `db.py` migration list only. **Resolved in `18720b7`, and the class of defect is now
  covered by `test_schema_convergence.py`.** Retained as motivation, not as an open item.

Both are the same class: a field added to some of its homes and not the rest. Neither is
findable by reading unless you already suspect it. The remaining checks below cover the field
lists; the schema columns are handled by the convergence test.

## Checks

Each check corresponds to an observed drift, not a hypothetical one.

### 1. ~~CREATE TABLE vs migration list~~ — SUPERSEDED

**Do not implement. Covered by `scripts/test_schema_convergence.py` (`fe1b55e`).**

As originally written this check compared the `db.py` `_apply_migrations` list against the
`CREATE TABLE` in `001_initial.sql`. **The premise was wrong on two counts.** The schema is three
files, not one — `001_initial.sql`, `002_v2_prompt_alignment.sql`, `003_funding_path.sql` — and
`_apply_migrations` *executes* 002 and 003 rather than duplicating their columns, so the
migration list never contains them. List-comparison was structurally incorrect, and widening it
to all three files would have broken it in the other direction.

`test_schema_convergence.py` replaced it with the right invariant: run `init_db` on a fresh DB, a
001-base DB, and every historical `data/*.db`, then assert all paths reach one canonical column
set. That tests the *outcome* rather than the bookkeeping, so it is immune to how migrations are
organised and survives a future `004`.

Retained here only so the check isn't reproposed.

### 2. Staging read vs observation read

Every field in `_FIELDS` that originates from HC extraction appears in `HC_FIELDS`, and vice
versa.

**Rationale:** this is the `round_size` failure. `decisions.md` — "Guarded Observation-Backed
Stage 9 Read Path" — made parity between the two loaders the acceptance criterion for keeping
the observation path, and its validation was "zero canonical transaction diffs." A field present
in one and absent from the other breaks that guarantee silently, and only manifests when the
read path is switched.

Fields legitimately exclusive to one path (derived-only, or sourced from a different stage)
should be declared in an explicit allow-list with a reason, not omitted.

### 3. Prompt output vs staging columns

Every field the extraction prompts declare in their output schema has a corresponding
`staging_extraction` column, and every `staging_extraction` column that receives extraction
output is declared by some prompt.

Covers `high_confidence_extraction`, `low_confidence_extraction`, `funding_hc_extraction`,
`deal_type_classifier`. (`funding_lc_extraction` was listed here until 2026-08-24; it never
became an executable contract and declares no fields to check.)

**Rationale:** this is the failure mode `handoff_hc_value_capture.md` is guarding against — a
prompt instructed to record a value into a field that has no home. Also catches the reverse: a
staging column nothing populates.

**Note:** likely the hardest check to implement, since prompt output schemas are prose plus a
JSON example rather than a machine-readable declaration. If parsing them proves brittle, a
maintained mapping is acceptable *provided the test fails when the mapping and the schema
disagree* — the point is that drift breaks a build, not that the extraction is elegant.

### 4. Derived fields have their inputs

Every field written by an aggregation derivation has its input fields present in `_FIELDS` and
`HC_FIELDS`.

**Rationale:** the `round_size` bug in one sentence — `_derive_investment_amount` reads
`round_size`, which wasn't in `HC_FIELDS`. A derivation whose inputs aren't loaded returns null
and looks like sparse data rather than a wiring fault.

## Allow-list — declared path exclusions

Fields legitimately exclusive to one path (derived rather than extracted). Each is declared here
**with a reason**, per `decisions.md` — "Observation Write Path Must Cover Every Field Aggregation
Reads" (2026-08-11). Checks 2 and 4 must treat these as expected exclusions, not drift. When
`scripts/test_field_parity.py` is built it consumes this list (mirror it as a code constant whose
divergence from this doc itself fails a test).

| Field | Excluded from | Reason |
|---|---|---|
| `consideration_type` | staging read (`_FIELDS`) / observation read | Derived by `_derive_consideration_type` from `consideration_components`; the HC-extracted value is intentionally ignored in favour of the derivation. `[verified: stages/aggregate.py — 2026-08-11]` |
| `round_stage_category` | staging read (`_FIELDS`) on the aggregation path | Derived by `_derive_round_stage_category` from `round_label`; `003_funding_path.sql` states this in a comment. `[verified: stages/aggregate.py:246, schema/003_funding_path.sql — 2026-08-11]` |

Neither is a drop. Both are extracted/stored but deliberately superseded by a derivation; the
allow-list records the intent so a future parity run does not flag them as missing wiring.

## Output

On failure: the field name, which sources have it, which don't, and which check failed.

On success: optionally emit the inventory — every field with the sources it appears in — as a
generated artefact. **Generated, never hand-maintained.** A committed inventory that isn't
regenerated is the same stale-document problem one layer down.

---

## Scope boundaries

**Not in scope:** field *definitions*, semantics, or whether a field is correct. This checks
that a field exists everywhere it needs to, not that it means the right thing. Semantics live in
`decisions.md` and the spec.

**Not a schema of record.** The DDL is the schema of record. This test asserts the other five
places agree with it.
